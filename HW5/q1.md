### Calculations 

For CPU est. latency in nano seconds equals the cylce count div by the freq in ghz which I choose 4ghz. 

```text
Time per cycle at 4 GHz = 1 / 4 = 0.25 ns

L1:  5 cycles / 4 GHz = 1.25 ns
L2: 15 cycles / 4 GHz = 3.75 ns
Branch example: 20 cycles / 4 GHz = 5 ns
```

The source lists L1 latency as 5 cycles and L2 latency as 15 cycles. I assumed a CPU speed of 4 GHz to convert these into nanoseconds, so a different CPU speed would give different results. For sequential reads, I estimated the transfer time by dividing the data size by the bandwidth:

```text
Memory:
1,000,000 bytes / 20,000,000,000 bytes/s
= 0.000050 s
= 50 μs

HDD:
1 MB / 285 MB/s
= 0.00351 s
= 3.51 ms

NVMe SSD:
1 MB / 6,800 MB/s
= 0.000147 s
= 0.147 ms
```

**Memory:** Assumed data read from DRAM at 20 GB/s. Reading data in cache could be faster. The 50 μs value is calculated not measured  [5][bandwidth]

**Storage:** The seq read est assume already going trasnfer and doesnt have HDD int seek and rotate delay. The SSD badnwidth may not be reach by a single 1 MB request.  [8][micron]

**HDD seeking:** The seek estimate comes from a 2019 Toshiba spec. Seeking moves the drive head and while rotational delay is the wait for the data to rotate into position. [7][toshiba]

**Datacenter networking:** The 2021 measurement used small messages on a 25 Gb/s network through one switch under tuned conditions. Other datacenter setups may have higher latency. [6][homa]


## Which improved the most
The best improvement in these examples is the transfer time for big storage reads esp when moving from HHD to SSD. Short datacenter roundtrips also improved in this benchmark. Seq memory reads benefit from higher bandwidth. DRAM access that is induvial, branch mispredciton recovry, and hdd seeks are about the same. Internation comm remains around the same and still expensive. These comparisons show that increasing bandwidth help with large transfers but it does not get rid of the cost of waiting for dependent memory access or distance response.
